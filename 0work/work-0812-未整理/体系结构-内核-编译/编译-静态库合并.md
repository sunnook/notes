我们有一个现有的对象库（OBJECT library）和静态库目标。现在，用户想要在构建静态库时，除了已有的对象库中的目标文件，还希望链接（添加）另一个预编译的静态库（即搜索并添加一个已有的静态库文件）。

 具体需求：
 1. 搜索一个外部静态库（例如，假设我们要链接一个名为 `libfoo.a` 的静态库）。
 2. 将这个外部静态库与现有的对象库（`${OBJECT_NAME}`）一起链接到静态库目标（`${STATIC_LIB_NAME}`）中。

 在CMake中，静态库不能直接“链接”另一个静态库（因为静态库实际上是目标文件的归档）。但是，我们可以通过以下两种方式之一实现：

 方法1：使用对象库（推荐）
   - 将外部静态库解包（提取出其中的目标文件），然后与当前的对象库一起打包成新的静态库。
   - 这种方法需要知道外部静态库的路径，并使用CMake命令解压。

 方法2：使用链接器包装（不推荐，因为可能复杂且不可移植）
   - 在某些平台上，可以通过链接器选项将多个静态库合并，但这不是标准做法。

 然而，更常见的做法是：让最终的可执行文件（或共享库）链接多个静态库。但这里用户要求将外部静态库“添加”到当前的静态库中。

 考虑到CMake的静态库本质上是归档文件，我们可以通过`add_library`创建静态库时，除了对象库的目标文件，还可以添加外部静态库中的目标文件（需要先解压）。但是，CMake本身不直接支持在`add_library`命令中解压静态库。

 替代方案：使用`add_dependencies`和自定义命令

 步骤：
 1. 使用`find_library`找到外部静态库。
 2. 创建一个自定义命令，使用归档工具（如`ar`）解压外部静态库到一个目录（得到目标文件列表）。
 3. 将这些目标文件添加到静态库的源文件中（与对象库的目标文件一起）。

 但是，这种方法很复杂，且可能不跨平台（尤其是在Windows上）。

 另一种更简洁的方法（在Unix-like系统上）：
   - 使用`add_library`创建一个新的目标，类型为`OBJECT`，将这个外部静态库解压得到的目标文件作为该对象库的源文件（实际上是已编译的目标文件）。
   - 然后将这个新的对象库与原有的对象库一起打包。

 然而，CMake并不支持直接添加已编译的目标文件作为源文件（除了通过`OBJECT`库的方式），而且解压静态库的操作需要自定义命令。

 因此，更简单且跨平台的做法是：不在构建时合并静态库，而是让最终的可执行文件同时链接这两个静态库。

 但是，如果确实需要合并，我们可以这样做（以Unix为例）：

 ```cmake
 # 假设找到外部静态库
 find_library(FOO_LIBRARY foo)
 # 创建一个自定义目标来解压静态库
 add_custom_command(
   OUTPUT ${CMAKE_CURRENT_BINARY_DIR}/foo_unpacked/foo.o
   COMMAND ${CMAKE_COMMAND} -E make_directory ${CMAKE_CURRENT_BINARY_DIR}/foo_unpacked
   COMMAND ar -x ${FOO_LIBRARY} -C ${CMAKE_CURRENT_BINARY_DIR}/foo_unpacked
   DEPENDS ${FOO_LIBRARY}
 )

 # 注意：解压后的目标文件可能有多个，这里假设只有一个foo.o（实际需要处理多个）
 # 获取解压后的所有目标文件
 file(GLOB FOO_OBJECTS "${CMAKE_CURRENT_BINARY_DIR}/foo_unpacked/*.o")

 # 然后，在创建静态库时，除了原有的对象库目标文件，还加上这些解压出来的目标文件
 add_library(${STATIC_LIB_NAME} STATIC
   $<TARGET_OBJECTS:${OBJECT_NAME}>
   ${FOO_OBJECTS}
 )
 ```

 但是，这种方法有很多缺点：
   - 外部静态库的文件名和路径可能因平台而异。
   - 解压出来的目标文件可能有冲突（比如两个静态库有同名目标文件）。
   - 在Windows上，静态库是`.lib`，而解压工具是`lib.exe`，命令不同。

 因此，通常不建议在构建过程中合并静态库。

 更推荐的做法是：将外部静态库作为单独的库目标，然后在链接最终可执行文件或共享库时同时链接这两个静态库。

 但是，如果用户坚持要合并，并且只考虑Unix-like系统，我们可以用上述方法。

 1. 使用`find_library`找到外部静态库。

 3. 然后，在创建最终的可执行文件或共享库时，同时链接原有的静态库和这个导入的静态库。

要在现有静态库中添加另一个预编译的静态库，需要通过 **目标链接依赖** 实现。以下是两种推荐方法（选择其中之一）：

---

### 方法1：使用 `target_link_libraries()` 添加依赖（推荐）
在静态库目标上声明依赖，CMake 会自动合并两个库：
```cmake
# 先找到需要添加的外部静态库
find_library(EXTERNAL_LIB 
  NAMES external_lib   # 库名（如 libexternal_lib.a）
  PATHS /path/to/lib   # 库的搜索路径
)

# 将外部库链接到你的静态库
target_link_libraries(${STATIC_LIB_NAME} PRIVATE ${EXTERNAL_LIB})
```

#### 原理：
- CMake 会在链接时执行 `ar -x` 解压外部库，将其目标文件合并到 `${STATIC_LIB_NAME}` 中
- 支持所有平台（Linux/macOS/Windows）
- 自动处理依赖关系

---

### 方法2：直接添加目标文件（需解压）
手动解压外部静态库并添加其目标文件：
```cmake
# 解压外部静态库到临时目录
add_custom_command(
  OUTPUT ${CMAKE_BINARY_DIR}/external_objects
  COMMAND ${CMAKE_AR} -x ${EXTERNAL_LIB_PATH}
  COMMAND mv *.o ${CMAKE_BINARY_DIR}/external_objects
)

# 获取解压后的目标文件
file(GLOB EXTERNAL_OBJECTS ${CMAKE_BINARY_DIR}/external_objects/*.o)

# 添加到静态库
add_library(${STATIC_LIB_NAME} STATIC 
  $<TARGET_OBJECTS:${OBJECT_NAME}>
  ${EXTERNAL_OBJECTS}  # 添加外部库的目标文件
)
```

#### 适用场景：
- 需要精细控制合并过程
- 需过滤特定目标文件（如只合并部分符号）
- 跨平台兼容性较差（需处理 `.o`/`.obj` 差异）

---

### 完整修改示例
```cmake
# 1. 创建对象库
add_library(${OBJECT_NAME} OBJECT ${OBJECT_SRC})

# 2. 查找外部静态库（以zlib为例）
find_library(ZLIB_LIB 
  NAMES z zlib 
  PATHS /usr/lib /usr/local/lib
)

# 3. 创建主静态库
set(STATIC_LIB_NAME ${PROJECT_NAME}-static)
add_library(${STATIC_LIB_NAME} STATIC 
  $<TARGET_OBJECTS:${OBJECT_NAME}>
)

# 4. 添加外部库依赖
target_link_libraries(${STATIC_LIB_NAME} PRIVATE ${ZLIB_LIB})

# 5. 设置输出名和安装
set_target_properties(${STATIC_LIB_NAME} PROPERTIES OUTPUT_NAME ${PROJECT_NAME})
install(TARGETS ${STATIC_LIB_NAME} ARCHIVE DESTINATION lib)
```

---

### 关键注意事项
1. **静态库合并本质**  
   实质是将外部库的目标文件（`.o/.obj`）解压并重新打包到新库中
   
2. **符号冲突处理**  
   如果两个库有同名符号，链接时会报错。解决方案：
   - 使用 `-Wl,--whole-archive`（Linux）
   - 重命名冲突符号

3. **跨平台命令差异**  
   | 平台       | 静态库工具 | 文件扩展名 |
   |------------|------------|------------|
   | Linux/macOS| `ar`       | `.a`       |
   | Windows    | `lib.exe`  | `.lib`     |

推荐优先使用 `target_link_libraries()`，它已处理了这些底层差异。

我们需要在CMake中创建一个新的库目标，这个新库会链接一些子库（静态库或动态库），并且我们希望这些子库的符号被完全包含在新库中，对外只暴露新库的接口。这通常称为“库的合并”或“库的嵌套链接”。

 对于静态库（.a 或 .lib）：
   1. 如果子库是静态库，我们可以将子库直接合并（打包）进新的静态库中。
   2. 但是，CMake默认在链接静态库时，并不会将子静态库的内容合并到父静态库中，而是形成依赖关系（在最终链接可执行文件时才会将需要的部分链接进去）。如果我们希望将子库完全打包进新的静态库，我们需要使用特定的工具（如ar）或者使用CMake的`OBJECT`库特性。

 对于动态库（.so 或 .dll）：
   1. 动态库在链接时，通常会将依赖的动态库作为运行时依赖（不会将代码合并），所以动态库无法将另一个动态库打包进去。

 因此，根据你的需求，如果你希望将子库完全打包进新的库中，那么新的库必须是静态库，并且子库也必须是静态库。

 解决方案：

 1. 使用CMake的`OBJECT`库（推荐）：
    OBJECT库将编译生成的.o/.obj文件组合成一个库，然后可以将多个OBJECT库合并成一个静态库。

 2. 使用静态库的合并命令（如Linux下的`ar`，Windows下的`lib.exe`）：
    在CMake中通过`add_custom_command`和`add_custom_target`来执行合并命令。

 下面分别说明这两种方法：

 方法一：使用OBJECT库

 假设我们有两个子库（sub1, sub2）和一个要生成的新库（mylib）。

 步骤：
   a. 将子库定义为OBJECT库：
      ```cmake
      add_library(sub1 OBJECT src1.cpp)
      add_library(sub2 OBJECT src2.cpp)
      ```

   b. 创建新的静态库，并将子库的OBJECT文件加入：
      ```cmake
      add_library(mylib STATIC
        $<TARGET_OBJECTS:sub1>
        $<TARGET_OBJECTS:sub2>
        # 还可以添加新的源文件
        src3.cpp
      )
      ```

   这样，mylib就会包含sub1和sub2的所有对象文件，以及src3.cpp的对象文件。

 注意：OBJECT库的源文件必须是编译为位置无关代码（PIC）的，如果主库是动态库，那么需要设置`POSITION_INDEPENDENT_CODE`属性。对于静态库，通常不需要PIC，但如果这个静态库将来可能会被链接到动态库中，则建议设置PIC。

 方法二：使用静态库合并命令（以Linux为例）

   a. 先分别编译子库为静态库：
      ```cmake
      add_library(sub1 STATIC src1.cpp)
      add_library(sub2 STATIC src2.cpp)
      ```

   b. 创建一个新的静态库目标，但先不指定源文件（或者指定一些额外的源文件）：
      ```cmake
      add_library(mylib STATIC src3.cpp)
      ```

   c. 在构建新库后，使用自定义命令将子库合并到新库中：
      ```cmake
      # 获取子库的路径
      get_target_property(SUB1_LIB sub1 LOCATION)
      get_target_property(SUB2_LIB sub2 LOCATION)

      # 设置合并后的库文件路径
      set(MERGED_LIB ${CMAKE_CURRENT_BINARY_DIR}/libmylib.a)

      # 使用ar命令合并（Linux）
      add_custom_command(TARGET mylib POST_BUILD
        COMMAND ${CMAKE_AR} -x ${SUB1_LIB}
        COMMAND ${CMAKE_AR} -x ${SUB2_LIB}
        COMMAND ${CMAKE_AR} -r ${MERGED_LIB} *.o
        WORKING_DIRECTORY ${CMAKE_CURRENT_BINARY_DIR}
        COMMENT "Merging static libraries into mylib"
      )
      ```

   注意：这个方法在不同平台需要不同的工具（Windows下使用`lib.exe`）且可能更复杂，而且可能不是所有平台都支持。另外，这种方法可能会遇到符号冲突的问题。

 总结：

 推荐使用OBJECT库的方法，因为它更跨平台，且由CMake原生支持。但是需要注意，如果子库本身不是由你控制的（例如第三方库），则可能无法将其转换为OBJECT库。在这种情况下，你可能需要先将其解压（提取出对象文件）再合并，这通常更复杂。

 另外，如果子库是动态库，那么无法合并到静态库中。所以，确保子库也是静态库。

 如果你希望生成动态库，那么无法将其他动态库打包进去，但可以通过链接依赖来使用。在动态库中链接静态库（将静态库合并到动态库）是默认行为（在Linux下，gcc在链接动态库时，会将链接的静态库中的代码合并到动态库中；在Windows下，静态库会被完全链接进动态库）。但是，如果链接的是动态库，则只会记录依赖关系。

 因此，如果你希望新库是动态库，并且希望将子库（静态库）打包进去，那么直接链接即可：
   ```cmake
   add_library(mylib SHARED src3.cpp)
   target_link_libraries(mylib PRIVATE sub1 sub2)
   ```

 这样，在Linux下，sub1和sub2的代码会被合并到mylib.so中；在Windows下，sub1和sub2的代码也会被合并到mylib.dll中。

 但是，如果子库是动态库，那么就不能被合并，只能作为运行时依赖。

 所以，根据你的需求，请选择适合的方式。

在 CMake 中，可以通过静态库合并的方式实现将子库完全打包进新的库文件中，使子库对外不可见。以下是完整解决方案：

### 解决方案：使用静态库合并

```cmake
# 1. 创建子库（静态库）
add_library(child_lib STATIC 
    child_source1.cpp
    child_source2.cpp
)

# 2. 创建主库（静态库）
add_library(main_lib STATIC
    main_source.cpp
)

# 3. 关键步骤：合并子库到主库
#    将子库的目标文件链接到主库
target_link_libraries(main_lib PRIVATE child_lib)

# 4. 设置链接属性，确保子库被完整包含
set_target_properties(main_lib PROPERTIES
    LINK_INTERFACE_MULTIPLICITY 3
    INTERFACE_LINK_LIBRARIES ""
)
```

### 关键原理说明：

1. **静态库合并机制**：
   - 当链接静态库（`.a`/`.lib`）到另一个静态库时
   - CMake 默认**不会**将子库代码嵌入主库
   - 但通过 `LINK_INTERFACE_MULTIPLICITY` 属性可强制完整包含

2. **属性设置作用**：
   - `LINK_INTERFACE_MULTIPLICITY 3`：强制主库包含所有链接的符号
   - `INTERFACE_LINK_LIBRARIES ""`：清除对外暴露的依赖关系

3. **最终效果**：
   - `main_lib` 会包含 `child_lib` 的所有目标代码
   - 外部用户链接 `main_lib` 时：
     - 不需要知道 `child_lib` 的存在
     - 不需要额外链接 `child_lib`
     - 看不到 `child_lib` 的符号暴露

### 替代方案：使用 OBJECT 库（更推荐）

```cmake
# 1. 将子库创建为 OBJECT 库
add_library(child_lib OBJECT
    child_source1.cpp
    child_source2.cpp
)

# 2. 创建主库时直接包含 OBJECT 文件
add_library(main_lib STATIC
    main_source.cpp
    $<TARGET_OBJECTS:child_lib>  # 关键：嵌入子库对象

### 1. 为什么 `aip_object` 不需要加 `${}`？
在 CMake 中，变量和目标是不同的实体。当我们使用 `add_library` 或 `add_executable` 创建目标时，我们给目标一个名字（例如 `aip_object`）。在后续的 CMake 命令中引用这个目标时，我们直接使用目标名（不带 `${}`），因为目标名本身就是一个 CMake 实体。

- 当引用一个目标（target）时，直接使用目标名（如 `aip_object`）。
- 当引用一个变量（variable）时，使用 `${变量名}`。

### 2. `--whole-archive` 的作用

`--whole-archive` 的作用是告诉链接器：接下来指定的静态库（或目标文件）中的所有目标文件（即所有符号）都应该被包含在输出中，无论它们是否被引用。然后，我们使用 `--no-whole-archive` 来恢复默认行为，以便后续的库仍然按默认方式处理。

    # 系统依赖
    m       # 数学库
    pthread # 线程库
    c       # C标准库（提供mem*/stack保护）
    dl      # 动态加载库（常见依赖）
)
```

#### 2. 对象库方式修正（完整方案）

```cmake
# 创建主静态库（不含AIP）
add_library(alg_neteq STATIC
  $<TARGET_OBJECTS:your_objects>
)

# 在最终目标中组合依赖
add_executable(your_final_executable main.cpp)

target_link_libraries(your_final_executable PRIVATE
  alg_neteq  # 主算法库
  
  # AIP 库及其依赖
  -Wl,--whole-archive
  ${CMAKE_CURRENT_SOURCE_DIR}/lib/F5Plus/libAIP_F5Plus.a
  -Wl,--no-whole-archive
  
  m pthread c dl
)

# 添加安全编译选项
target_compile_options(your_final_executable PRIVATE
  -fstack-protector-strong  # 匹配AIP的栈保护
)
```

### 为什么对象库方式之前失败

1. **依赖未传递**:
   ```cmake
   # 对象库方式只包含代码，不包含依赖信息
   add_library(combined STATIC
     $<TARGET_OBJECTS:alg_neteq>
     $<TARGET_OBJECTS:aip_objects>  # 缺少依赖信息!
   )
   ```

2. **栈保护不匹配**:
   AIP 库使用了 `__stack_chk_*` 符号，需要：
   - 链接时包含标准C库(`libc`)
   - 编译时启用 `-fstack-protector`

### 验证命令

1. 检查最终可执行文件符号：
```bash
aarch64-linux-gnueabihf-f5plus-nm -C your_final_executable | grep -E 'AIP_|__stack_chk_'
```

2. 检查栈保护：
```bash
# 应该显示stack protector已启用
readelf -s your_final_executable | grep stack_chk
```

### 备选方案：封装成接口库

```cmake
# 创建AIP接口库
add_library(aip_interface INTERFACE)
target_link_libraries(aip_interface INTERFACE
  -Wl,--whole-archive
  ${CMAKE_CURRENT_SOURCE_DIR}/lib/F5Plus/libAIP_F5Plus.a
  -Wl,--no-whole-archive
  m pthread c dl
)

# 主目标使用
target_link_libraries(your_final_executable PRIVATE
  alg_neteq
  aip_interface
)
```

这个方案能确保：
1. 所有AIP依赖被正确传递
2. 栈保护机制一致
3. 内部符号完整解析
4. 保持CMake的模块化设计
