*   **为什么防AI**：内核开发调试极难，动辄panic，且与硬件交互极深。AI写不了可靠的内核驱动。

### 一、 音视频骨架有哪些？如何了解和调试？

在端侧（以Android为例），所谓的“音视频骨架”，就是**数据从物理世界被采集，到变成字节流送入网络发送器**的这条完整链路。UI只是这条链路最后展示的一个小尾巴。

这条骨架由四大模块构成：**采集 -> 前处理 -> 编解码 -> 传输封装**。

#### 1. 采集
*   **视频**：Camera2 / CameraX API。核心是搞懂如何获取原始的 YUV 数据（通常是 NV21 或 YV12），而不是压缩后的 JPEG。
*   **音频**：AudioRecord API。核心是搞懂采样率、位深、声道数，拿到原始的 PCM 数据。
*   **如何了解**：写一个极简的 Demo，不要任何界面，只在后台跑。摄像头预览用 SurfaceTexture 接收，音频用 AudioRecord 循环读。
*   **如何调试（核心大招：Dump 裸流）**：
    *   **这是音视频工程师最基本也是最核心的调试手段！** 
    *   把 Camera 回调里拿到的 YUV 数据，直接用 `FileOutputStream` 写入手机存储（比如 `sdcard/dump.yuv`）。
    *   把 AudioRecord 读到的 PCM 数据，写入 `sdcard/dump.pcm`。
    *   导出到电脑，用 **FFplay** 或 **Elecard** 直接播放验证：`ffplay -f rawvideo -pixel_format nv21 -video_size 640x480 dump.yuv`。如果能看到图像，说明采集链路完美；如果是花屏，说明格式或宽高传错了。这比在手机屏幕上看一万遍都准。

#### 2. 前处理
*   **视频**：OpenGL ES / Vulkan。做裁剪、缩放、滤镜、美颜。核心是搞懂 EGL 环境、Shader 编写，以及最关键的：**如何把 OpenGL 处理后的纹理，读回 CPU 内存（glReadPixels）或者直接交给硬编**。
*   **音频**：回声消除（AEC）、降噪（NS）、自动增益（AGC）。WebRTC 的音频处理模块（APM）是行业标杆。
*   **如何了解**：重点学习 Android 的 `SurfaceTexture` 机制，理解纹理如何在 GPU 和 CPU 之间高效传递。
*   **如何调试**：视频依然靠 Dump OpenGL 处理后的 YUV；音频靠接上 WebRTC 的 APM 模块后，Dump 处理前后的 PCM 对比听。

#### 3. 编解码—— **端侧最厚的护城河**
*   **硬编硬解**：Android MediaCodec API。这是你必须要死磕的骨架。
*   **如何了解**：搞懂输入输出缓冲区，搞懂 `dequeueInputBuffer` / `queueInputBuffer` 的异步流程。**最重要的是搞懂输出格式**：MediaCodec 吐出来的是 AVCC 格式还是 AnnexB 格式？SPS/PPS 哪里拿？为什么给 SRS 推流必须把 AVCC 转成 AnnexB？
*   **如何调试**：
    *   **看 MediaCodec 的状态机日志**：`adb logcat -s MediaCodec`。
    *   **Dump 编码后的 H.264/H.265 裸流**：把 MediaCodec 输出的 byte[] 直接写文件 `sdcard/dump.h264`。用 FFplay 播放：`ffplay dump.h264`。如果绿屏，大概率是 SPS/PPS 没拼对或者格式转换错了。

#### 4. 传输封装
*   把编码后的 H.264 封装成 FLV 还是拆解成 RTP 包？音频 Opus 怎么打包？
*   **如何了解**：看 SRS 的 WHIP 推流协议规范，看 RFC 文档。
*   **如何调试**：抓包，前面讲过的 Wireshark，这是唯一途径。

**总结：了解骨架的方法是“顺藤摸瓜写极简Demo”，调试骨架的终极手段是“Dump裸流 + PC端验证”。**

### 二、 Linux内核感觉都会问的，怎么应对？

你的直觉是对的：**面试中高级流媒体/后端岗位，Linux内核必问。**

但你的策略可能是错的：**千万不要去啃《深入理解Linux内核》那种砖头书，那是给写操作系统的人看的，你是写流媒体的，看那种书只会让你从入门到放弃。**

面试官问内核，不是想听你背源码，他想考察的是：**当线上出现诡异的性能瓶颈或网络丢包时，你有没有能力穿透应用层，去内核里找答案。**

你只需要掌握流媒体视角的**三个内核子系统**，并准备好对应的“排障故事”：

#### 1. 网络子系统（必考中的必考）
流媒体就是玩网络的，这块必须门清。
*   **高频考点**：epoll 的 LT（水平触发）与 ET（边缘触发）区别？为什么 ET 必须用非阻塞 IO？TCP 的拥塞控制与流控？UDP 收包为什么会丢？
*   **内核排障实战（面试加分项）**：
    *   **现象**：SRS 高并发时，UDP 丢包严重，但带宽没跑满。
    *   **排查**：`netstat -s` 看到大量的 `packet receive errors`；`cat /proc/net/udp` 看到丢包。
    *   **内核解法**：增大 UDP 接收缓冲区。`sysctl -w net.core.rmem_max=16777216` 和 `net.core.rmem_default=16777216`。面试时把这个参数和排查过程甩出来，面试官知道你干过真活。

#### 2. 中断与调度子系统
流媒体服务器单机扛十万路并发时，瓶颈往往在软中断。
*   **高频考点**：进程上下文切换开销？软中断是什么？
*   **内核排障实战**：
    *   **现象**：`top` 命令发现 CPU 的 `si`（软中断）占比极高，接近 100%，机器卡死。
    *   **排查**：`cat /proc/softirqs` 发现网络收发的软中断全集中在 CPU 0 上。
    *   **内核解法**：开启 RPS（Receive Packet Steering），把网络包的软中断打散到多核处理。`echo fffe > /sys/class/net/eth0/queues/rx-0/rps_cpus`。这招是高并发流媒体服务器的标配。

#### 3. 内存子系统
*   **高频考点**：内存分配原理？什么是内存碎片？什么是零拷贝？
*   **内核排障实战**：
    *   **现象**：SRS 转发大量视频流时，内存暴涨不释放。
    *   **排查**：关注 Slab 缓存（`slabtop` 命令），看是不是 `kmalloc-2048` 这种内核对象占满了。了解页缓存和脏页回写机制（`pdflush` 线程）。

#### 面试应对策略：准备你的“内核排障三板斧”

面试时，不要等面试官问“你了解Linux内核吗”，你要主动把内核知识融合在你的项目经验里。

**话术模板：**
> “在海康做对讲/做SRS推流时，我遇到过一次高并发丢包问题。起初以为是应用层处理慢，但我通过 `cat /proc/net/udp` 和 `netstat -s` 定位到是内核 UDP 缓冲区溢出。最后通过调整 `net.core.rmem_max` 这个内核参数解决了。这让我意识到，做流媒体不能只懂应用层 API，必须懂内核的网络收发机制。”

**总结：把 Linux 内核当成你的“X光机”，不需要你会造 X 光机，但你必须会看 X 光片。** 带着问题（丢包、高CPU、内存泄漏）去查内核参数和 /proc 文件系统，这是最高效的路径。

### 1. 你的“多层架构”是为了什么？

你之前写的 `native -> data -> domain -> di -> ui`，这是典型的 **Clean Architecture**（整洁架构），或者说是 MVVM/MVI 的变体。

这种架构解决的核心痛点是：**业务逻辑的复杂度和 UI 的解耦**。
*   你怕 UI 变了，业务逻辑跟着改。
*   你怕数据源换了（比如从本地换到网络），UI 层要重写。
*   你需要依赖注入（DI）来方便写单元测试。

**但音视频引擎有这些痛点吗？没有！**

音视频引擎的核心是**数据流**，不是**业务逻辑**。
*   你的输入是摄像头/麦克风的裸数据（YUV/PCM）。
*   你的输出是编码后的网络流（H.264/AAC RTP包），或者解码后的渲染帧。
*   这中间的过程是：采集 -> 前处理（美颜/降噪） -> 编码 -> 封装 -> 传输。

**在这个链路里，没有 UI，没有 Domain，没有 Data 层，只有“处理节点”和“数据管道”。**

如果你在写一个美颜滤镜时，还要把数据从 C++ 的 Native 层回调到 Java 的 Data 层，再流转到 Domain 层，再丢给 UI 层去渲染，**那延迟早就爆表了，视频绝对卡成PPT。**

你说的“在浏览器调”，我猜是指 WebRTC 那套东西，或者前端播放器（比如 `<video>` 标签 + HTTP-FLV/HLS）。

1.  **你看不到底层状态**：浏览器不会告诉你，当前 WebRTC 底层的 JitterBuffer 为什么积压了 500ms 的延迟；它只会告诉你延迟很高。

### 3. 音视频引擎的“分层”和“调试”是怎样的？

在音视频引擎里，确实也有“分层”，但完全不同于你熟悉的业务分层：

| 你的应用架构 | 音视频引擎架构 | 核心区别 |
| :--- | :--- | :--- |
| **UI 层** (展示) | **渲染层** (OpenGL/Metal/SurfaceView) | UI 层关心布局和点击；渲染层只关心如何把 YUV/RGB 数据以最快速度画到屏幕上，避免撕裂和卡顿。 |
| **Domain 层** (业务) | **处理/编解码层** (FFmpeg/WebRTC Native) | Domain 层关心用户有没有登录；处理层关心 H.264 的 B 帧怎么解码，回声怎么消除。 |

### 1. 我说的引擎，是服务端还是客户端的？

我说的**主要是客户端引擎**，但也离不开服务端。

你要建立一个核心认知：**在实时音视频（RTC）领域，客户端引擎才是真正的“大脑”，服务端更多是“四肢”。**

为什么？
*   **服务端引擎（如 SRS、MediaSoup）**：主要负责流的转发（SFU）、混流（MCU）、录制。它在弱网下的作用是“配合”，比如服务端发现客户端丢包，帮忙重传（NACK）；或者根据客户端的带宽估计，服务端下发对应清晰度的流（Simulcast/SVC）。**服务端不产生数据，只搬运数据。**
*   **客户端引擎（如 WebRTC Native）**：负责**采集、前处理、编码、发送、接收、解码、后处理、渲染**。弱网对抗的核心决策者在这里。网络抖动了，是降帧率还是降分辨率？是加 FEC 冗余还是请求重传？JitterBuffer 积压了，是加速播放还是丢弃晚到的包？**这些关乎体验的“生死决策”，全在客户端引擎里。**

所以，当你作为引擎开发者去改 FEC、改 Pacing 时，你改的是**客户端的 C++ 代码**。

### 2. 浏览器里改不了，那我应该怎么改？在哪里调？

这就是最核心的实操问题了。

**浏览器（Chrome/Safari）是一个被封装好的“黑盒”**。它把 WebRTC 的底层能力通过 JavaScript API（`RTCPeerConnection`）暴露出来，你只能在它画好的圈圈里跳舞（比如改改 SDP 里的 max-bitrate，或者设置一下 preferred codec）。你要想动 FEC 的算法、Pacing 的逻辑，**浏览器绝对不允许**，因为浏览器要保证安全、稳定和跨平台一致性。

**你要想真正掌控这些，只有一条路：跳出浏览器，进入 Native 世界（C/C++）。**

具体怎么做？有以下三条路径，难度递增，控制力也递增：

#### 路径一：使用开源的 WebRTC Native 源码（最正统，也最难）

这是最硬核、最彻底的方法。WebRTC 本身就是开源的，你可以把它的 C++ 源码编译成动态库，然后在 Android（通过 JNI）或 iOS 上跑。

**在哪里调？**
在 WebRTC 的 C++ 源码里调。

*   **改 FEC 冗余度**：
    去找 `webrtc/src/modules/rtp_rtcp/source/fec_generator_impl.cc` 或相关的 UlpFEC/FlexFEC 生成代码。
    WebRTC 默认的 FEC 冗余度是根据丢包率动态计算的。如果你觉得它太保守（弱网下还是卡），你可以直接修改计算冗余度的公式。比如，原来丢包率 10% 时只加 20% 的冗余，你强行改成加 40% 的冗余。
*   **改 Pacing（平滑发送）算法**：
    去找 `webrtc/src/modules/pacing/pacing_controller.cc`。
    Pacing 的作用是把突发的大包（如 I 帧）均匀打散到时间轴上发送，避免瞬间塞满路由器队列导致丢包。你可以调整它的发送间隔、桶大小，甚至在弱网时故意压低 Pacing 速率来迎合拥塞控制。

**怎么调？**
1.  **编译源码**：拉取 WebRTC 源码（几十个 G），配置环境，编译出你自己的 `libwebrtc.aar` 或 `.framework`。
2.  **加埋点**：在 C++ 层把 FEC 的冗余度、Pacing 的队列深度、实际的发送码率，通过回调抛给 Java 层，展示在你的 App 调试面板上。
3.  **模拟弱网**：用 Linux 的 `tc` 命令（如 `tc qdisc add dev eth0 netem loss 20% delay 100ms`）在手机连接的 Wi-Fi 热点上制造丢包和延迟。
4.  **对比验证**：修改 C++ 代码 -> 重新编译 -> 跑 App -> 看弱网下的面板数据是否按你的预期变化，画面是否更流畅。

#### 路径二：自研轻量级引擎（基于 C/C++ 开源库拼装）

WebRTC 太庞大（几千万行代码），编译一次半天。很多大厂（如字节、腾讯）都是自研引擎，或者基于 WebRTC 大刀阔斧裁剪。

**在哪里调？**
在你自己写的 C++ 代码里。

*   **网络传输层**：不用 WebRTC 的 RTP/SRTP 栈，自己基于 `libuv` 或 `boost::asio` 写 UDP 收发。
*   **FEC**：引入开源的 FEC 库（如 `openfec` 或 RS 纠错码库），自己写逻辑判断：当前网络丢包率是多少，我该传多少冗余包给对端。
*   **Pacing**：自己写一个令牌桶算法，控制 `sendto()` 的调用频率。

**怎么调？**
这种方式最灵活，因为代码全是你自己写的。你在 Android Studio 或 Xcode 里直接断点 C++ 代码，用 LLDB/GDB 单步调试。配合 `tcpdump` 在手机上抓包，用 Wireshark 在电脑上看 RTP 序列号，分析包间隔是否被 Pacing 抹平了。

#### 路径三：使用第三方商业 SDK 的底层接口（折中方案）

如果你觉得改 WebRTC 源码太难，自研又没时间，可以用声网、腾讯TRTC这样的 SDK。但注意，**你不能用它们的高级 API**（如 `joinChannel` 一键入会），那种 API 和浏览器一样是黑盒。

你必须用它们的**底层 API（Custom Audio/Video Source/Sink）**：
1.  自己用 C++ 做采集和编码。
2.  把编码后的 H.264 NALU 喂给 SDK 的发送接口。
3.  在发送前，**你自己加上 FEC 和 Pacing 逻辑**（这就回到了路径二）。
4.  接收端拿到的也是裸 NALU，你自己解码渲染。

### 1. 直接从 libwebrtc 拿 YUV 送到 SurfaceView 播出来？不需要 UI？

**错！大错特错！谁告诉你把 YUV 拿到 Java 层再画到 SurfaceView 的？**

这就是典型的应用层思维：“数据要在 UI 层才能显示”。
在音视频引擎里，**数据绝不能往上抛，必须在底层直接消化掉**。把每秒 30 帧、一帧好几兆的 YUV 数据从 C++ 通过 JNI 回调到 Java，再让 Java 用 Canvas 或 Bitmap 画上去，你的 App 瞬间就会因为内存拷贝和 GC 卡死。

**真实的引擎渲染流程是这样的：**

1.  **SurfaceView 确实是 UI 组件，但引擎用的不是它的“画布”，而是它的“表面（Surface）”。**
2.  在 Android 端，Java 层创建一个 `SurfaceView`，然后通过 `surfaceView.getHolder().getSurface()` 拿到底层的 `ANativeWindow` 指针（这是一个 C 结构体）。
3.  把这个指针通过 JNI 传给 C++ 层的 WebRTC 引擎。
4.  **C++ 层直接操作这个指针**：解码出 YUV 后，在 C++ 层直接调用 OpenGL ES 或 Vulkan，把 YUV 转换成 RGB，直接渲染到这个 `Surface` 对应的屏幕缓冲区上。

**结论：你需要 UI 吗？需要，但只需要一个“空洞”——一个没有任何绘制逻辑的 SurfaceView。** 所有的绘制逻辑全在 C++ 里完成。Java 层的 UI 线程完全解放，哪怕 Android 界面卡死了，视频画面依然流畅，因为它们跑在完全不同的线程和渲染管线里。

*(补充：如果你想拿 YUV 做美颜，也是在 C++ 层拿到 YUV -> 处理 -> 渲染，绝不会抛给 Java 层处理)*

### 2. 对于回放（加速、调变）等业务呢？

你用了“业务”这个词，说明你还在用 App 开发的视角看问题。

在音视频引擎里，**没有“业务”，只有“算法”和“流控”。**

加速（倍速）、调变（变调/变声），这听起来像是播放器的功能，但在底层，它们是极其硬核的**数字信号处理（DSP）**。并且，**实时通信（RTC）和流媒体回放（VOD）在处理这些需求时，架构是完全不同的。**

#### 场景 A：流媒体回放（VOD，比如看录播、看视频）
如果你做的是类似 IjkPlayer / FFplay 这种回放引擎，倍速和变调是这样实现的：

*   **视频倍速**：本质是**丢帧或改时间戳**。
    *   2倍速时，原本 40ms 一帧的画面，你把 PTS（显示时间戳）除以 2，让渲染器每隔 20ms 就画一帧。或者更暴力点，直接丢掉一半的 B 帧/P 帧，只解 I 帧和部分 P 帧。
*   **音频倍速（重点）**：这是难点。你直接把音频播放速度乘2，声音会变成“花栗鼠”（变尖了）。用户要的是“快但声音不变调”（Time-Stretching）。
    *   **怎么做？** 必须在 C++ 层引入 **SoundTouch** 或 **Sonic** 这种专业的音频处理库。
    *   **数据流**：解码出 PCM -> 送入 SoundTouch 设置 `tempo=2.0`（改变节奏但不改音调） -> SoundTouch 内部通过 WSOLA（波形相似度叠加）算法重新拼接 PCM 波形 -> 输出变长/变短的 PCM -> 送入音频设备播放。
*   **调变（变声/萝莉音/大叔音）**：同样是 SoundTouch，设置 `pitch=1.5`（提高音调），或者用更复杂的 RNN/VC 算法提取特征再重建。

**在这个场景下，你的架构依然是空壳 UI：**
Java 层拖动进度条 -> 传给 C++ `setSpeed(2.0f)` -> C++ 内部调整视频 PTS 策略，并把音频 PCM 接入 SoundTouch 管道 -> 渲染播放。

#### 场景 B：实时通信（RTC，比如视频会议）
如果你做的是 WebRTC 这种实时通话引擎，**绝对不能随意做倍速！**

实时通话的核心是“低延迟”，音视频必须绝对同步于采集时的绝对时间。如果你在通话时把对方的声音 2 倍速播放，你会瞬间打断对方的说话节奏，且音视频会彻底失步。

**RTC 里的“变速”是被动发生的，叫 JitterBuffer 的加速播放：**
当网络抖动，缓冲区里积压了 500ms 的音频数据时，为了追回延迟，WebRTC 的 NetEQ 模块会悄悄把音频以 1.1x 或 1.2x 的速度播放（利用 WSOLA 算法拉伸），或者直接丢弃部分静音包，直到缓冲区恢复正常。**这是底层自动的弱网对抗算法，对上层完全透明。**

**RTC 里的“调变”是主动的前处理：**
比如你想在通话中变声。你绝不能在解码后变声，因为那会引入延迟。
必须在**采集后、编码前**做处理：麦克风采集 PCM -> C++ SoundTouch/变声算法处理 -> 编码 -> 发送。

### C++ 底层怎么把数据给 UI？（防坑指南）

既然要做仪表盘，C++ 就得把数据传给 Java。这里千万要注意：**绝对不能高频传大对象！**

**错误做法**：C++ 每秒把一帧 YUV 传给 Java 去算帧率。
**正确做法**：C++ 在底层自己算好所有数据，只把结果（几个 int）传上去。

在 C++ 里建一个结构体：
```cpp
struct EngineStats {
    int fps = 0;
    int bitrate_kbps = 0;
    int packet_loss_percent = 0;
    int rtt_ms = 0;
    int fec_percent = 0;
};
```

在 C++ 里开一个定时器线程（或者挂在现有的模块里），每秒统计一次这些数据，然后通过 JNI 回调：
```cpp
// C++ 层
void onStatsUpdate(const EngineStats& stats) {
    // 通过 JNI 调用 Java 层的方法
    JNIEnv* env = ...;
    jobject callback = ...;
    jclass cls = env->GetObjectClass(callback);
    jmethodID mid = env->GetMethodID(cls, "updateUI", "(IIIII)V");
    // 只传 5 个 int，极其轻量，绝不卡顿
    env->CallVoidMethod(callback, mid, stats.fps, stats.bitrate_kbps, stats.packet_loss_percent, stats.rtt_ms, stats.fec_percent);
}
```

Java 层拿到这 5 个数字，直接 `textView.setText()` 刷新界面。
