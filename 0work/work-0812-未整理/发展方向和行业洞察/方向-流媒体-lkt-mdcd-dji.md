### 1. LiveKit 使用安卓的 MediaCodec 吗？和 WebRTC 如何交互的？

**结论：是的，LiveKit 在 Android 平台上最终是通过 WebRTC 引擎来间接使用 MediaCodec 的。**

#### 详细交互原理：

LiveKit 本身是一个基于 WebRTC 构建的实时通信平台（服务端用 Go 编写，基于 Pion）。当你在 Android 设备上使用 LiveKit 的客户端 SDK 时，底层的媒体处理完全依赖于 Google 的 WebRTC Native 库（编译进 SDK 的 `.so` 文件或 `.aar` 包中）。

**LiveKit、WebRTC 与 MediaCodec 的交互流程如下：**

1.  **业务与信令层（LiveKit 负责）**：
    *   LiveKit SDK 负责与 LiveKit 服务器建立 WebSocket 连接，处理房间管理、权限验证、订阅发布逻辑。
    *   它决定“谁应该接收谁的视频”，但这只是**信令控制**，不涉及实际音视频数据。
2.  **媒体管线建立（WebRTC 负责）**：
    *   当需要发布本地视频时，LiveKit SDK 调用 WebRTC API 创建 `PeerConnection` 和 `VideoTrack`。
    *   摄像头采集到的画面（通常是通过 `Camera2` API 获取的 YUV/RGB 数据）被送给 WebRTC 的 `VideoCapturer`。
3.  **硬件编解码调用**：
    *   WebRTC 内部有一套**硬件编解码器工厂**。
    *   在 Android 平台上，WebRTC 会自动检测设备支持的硬件编解码器，并实例化 `MediaCodecVideoEncoder`（编码）和 `MediaCodecVideoDecoder`（解码）。
    *   **编码过程**：WebRTC 将摄像头采集的原始帧通过 `Surface` 或 `ByteBuffer` 喂给 Android 的 `MediaCodec`（配置为 H.264 或 VP8/VP9 编码）。`MediaCodec` 利用 GPU/DSP 进行硬编码，输出压缩后的 H.264 码流（NALU）。
    *   WebRTC 将这些码流打包成 RTP 包，通过 SRTP 发送给 LiveKit SFU 服务器。
4.  **解码过程**：
    *   接收端 WebRTC 收到 RTP 包，解包还原成 H.264 码流，送入 `MediaCodec` 的解码输入端。
    *   `MediaCodec` 硬解后，将画面渲染到目标 `SurfaceView`/`TextureView` 的 `Surface` 上。

**总结**：LiveKit 不直接调用 `MediaCodec`，而是调用 WebRTC 的 Java/C++ API，WebRTC 内部封装了对 Android `MediaCodec` 的调用。这种设计保证了跨平台的一致性和极高的执行效率。

### 2. 大疆嵌入式音视频是用的什么平台？方案如何？是高度定制还是二次开发？Team 要求？

大疆在音视频领域的技术壁垒非常高，其方案属于**深度定制与底层自研**，远超一般的“拿开源库二次开发”。以下是具体的架构剖析：

#### (1) 使用的平台：Linux + RTOS 混合架构
大疆的无人机、云台相机等产品通常不是单一的“安卓”或“纯 Linux”，而是异构多核架构：
*   **实时控制系统 (RTOS)**：飞控、电机增稳、图传链路等对实时性要求极高的模块，通常运行在 RTOS（如 FreeRTOS 或大疆自研的 RTOS）上，甚至直接跑在 MCU 或 DSP 上。
*   **多媒体与应用层**：
    *   早期和部分专业航拍机：使用定制化的 **Linux**（如基于 Buildroot 裁剪的 Yocto/Linux）。
    *   带屏遥控器/行业应用平板：部分会使用深度定制的 **Android** 系统。
    *   相机核心 SoC：大疆很早就自研或深度联合定制芯片（如大疆自研的影像处理芯片），或者采用高通、安霸等高端 ISP/SoC，这些芯片通常运行裁剪过的 Linux。

#### (2) 音视频方案：高度定制为主，现有库为辅
大疆的图传和影像系统是其核心竞争力，绝对不可能直接用 FFmpeg + WebRTC 这种通用方案。

*   **视频编解码**：
    *   底层绝对使用**硬件编解码**（SoC 内置的 VPU/HardEncoder）。
    *   大疆不会直接调 Android 的 MediaCodec，而是直接操作 Linux 内核层的 V4L2 接口或厂商提供的私有驱动，以实现极低的延迟和极高的码率控制。
*   **图传协议**：
    *   大疆的 OcuSync 图传协议是**完全自研**的，基于自定义的物理层和 MAC 层优化，使用 OFDM 等技术。它不是标准的 WebRTC 或 RTMP，而是针对抗干扰、远距离、低延迟（做到百毫秒以内）深度定制的私有协议。
*   **封装与处理**：
    *   在本地录制时，可能会使用 MP4 封装，这部分可能借鉴了开源库（如 MP4v2 或轻量级封装），但音视频同步逻辑、码流复用都是自己写的。
    *   图传传输过程中的码流（通常是 H.264/H.265 裸流或自定义切片）直接通过自研协议打包发送，不经过传统的 FLV/RTSP 封装，以节省延迟。

#### (3) Team 要求如何？
大疆的嵌入式音视频团队属于行业顶尖水平，要求非常苛刻，通常包括：

1.  **语言基础**：精通 **C/C++**，熟悉内存管理、多线程并发。对汇编优化（ARM NEON 指令集）有一定了解以应对性能瓶颈。
2.  **系统底层能力**：
    *   精通 **Linux 内核驱动**和底层机制。
    *   熟悉 V4L2、ALSA、DRM/KMS 等多媒体子框架。
    *   精通进程间通信（Binder、共享内存、Socket），因为采集、编码、传输往往分布在不同的 CPU 核心和进程中。
3.  **音视频专业素养**：
    *   深入理解 H.264/H.265 协议规范（SPS/PPS、NALU、I/P/B 帧结构、码率控制策略如 CBR/VBR/ABR）。
    *   熟悉 ISP（图像信号处理）流程、3A 算法（AWB/AE/AF）。
    *   了解音频处理（AEC 回声消除、ANS 降噪、AGC 自动增益）。
4.  **性能与优化能力**：
    *   能够使用 perf、ftrace、systrace 等工具进行系统级性能瓶颈分析。
    *   具备**硬实时系统**的开发思维，能将端到端延迟压榨到极致。
5.  **网络与传输**：
    *   如果涉及图传或网络推流，需精通 RTP/RTCP、UDP/TCP、拥塞控制算法（如 GCC）、FEC 前向纠错和 ARQ 重传机制。

**总结**：大疆的嵌入式音视频开发极少是“调参侠”或“API 调用者”，而是要求深入到协议层、内核驱动层和硬件寄存器层，解决极端环境下的抗干扰、低延迟和高画质问题。

### 1. 切入大疆的话，LiveKit 上的纯应用级 QoS 优化有帮助吗？

**结论：直接的技术栈复用帮助有限，但底层思维和网络协议的理解有极大帮助。**

要理解这个问题，需要区分“应用级 API 调用”和“QoS 核心算法”。

*   **为什么直接帮助有限？**
    LiveKit 在 Android/客户端侧的 QoS 优化，通常是在 WebRTC 框架之上进行的。比如：动态调整分辨率/帧率（Simulcast/SVC）、根据网络反馈切换 Track、或者在应用层做一些丢包重传的策略参数配置。而大疆的图传是**完全自研的底层协议（OcuSync）**，跑在定制的物理层和 MAC 层上，不使用 WebRTC 那一套标准的 ICE/DTLS/SRTP 协议栈。大疆的 QoS 是直接在内核态或硬件编码器旁边做深度绑定的。所以，你在 LiveKit 上层写的 Java/Kotlin 代码，大疆根本用不上。
*   **为什么说思维和理解有极大帮助？**
    QoS（服务质量）的核心本质是相通的：**如何在不可靠的网络下，利用有限的带宽，保证音视频的实时性和画质。**
    如果你在做 LiveKit QoS 优化时，深入研究了以下内容，这些经验对大疆是**高度认可**的：
    1.  **带宽估计算法**：你是否理解 WebRTC 中的 GCC（Google Congestion Control）算法？是否知道如何通过延迟梯度变化和丢包率来预测可用带宽？
    2.  **码率控制**：当网络变差时，你如何通知编码器降码率？是否理解 H.264/H.265 的 QP（量化参数）调整机制？
    3.  **抗丢包机制**：你是否了解 FEC（前向纠错）和 NACK/ARQ（重传）的权衡？在什么延迟和丢包率下该用哪种？
    4.  **抖动缓冲**：你如何处理网络抖动导致的音视频不同步？

**切入大疆的建议：** 如果你想从 LiveKit 跳槽大疆，不要强调你“会用 LiveKit 的 API 做了什么上层控制”，而要强调你“**为了解决 LiveKit 某个卡顿问题，深入扒了 WebRTC Native 层的 GCC/FEC 源码，理解了网络拥塞控制原理**”。大疆看重的是你解决底层问题的能力，而不是你用了什么高级框架。
