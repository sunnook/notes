</think>在Linux驱动开发中，“映射”和“取消映射”通常涉及内存管理、DMA（直接内存访问）以及I/O内存访问。如果驱动程序在完成操作后**不执行 unmap（取消映射）**，具体后果取决于你使用的是哪种类型的映射。

以下是几种常见映射场景下，不 unmap 会导致的后果：

### 1. DMA映射 (DMA Mapping, 如 `dma_map_single` / `dma_map_page`)
这是驱动开发中最常见的不 unmap 导致严重问题的场景。
*   **内存泄漏与资源耗尽**：DMA映射会占用底层的系统资源（如IOMMU页表项、bounce buffer等）。如果不调用 `dma_unmap_single` 等函数，这些资源将永远无法释放。随着时间推移，系统可用的DMA资源会被耗尽，导致后续的DMA操作失败。
*   **数据不一致与损坏**：在某些架构上，DMA映射会刷新CPU缓存以保证设备和CPU的数据一致性。如果不 unmap，CPU缓存可能不会正确同步，导致CPU读到的是旧数据，或者设备写入了新数据但CPU不可见。
*   **系统崩溃（野指针/无效访问）**：如果底层内存被释放或重新分配，但DMA映射仍然存在并指向该物理地址，设备再次进行DMA操作时可能会把数据写到内核的其他关键数据结构中，直接导致 Kernel Panic。

### 2. I/O内存映射 (I/O Memory Mapping, 如 `ioremap` / `devm_ioremap`)
用于将设备的物理寄存器地址映射到内核虚拟地址空间。
*   **虚拟地址空间泄漏**：`ioremap` 会占用内核的虚拟地址空间（vmalloc area）。如果不调用 `iounmap`，这块虚拟地址空间将永久泄漏。虽然现代64位系统虚拟地址空间很大，但长期累积仍可能导致 `vmalloc` 失败。
*   **设备状态异常**：映射通常伴随着对设备寄存器的初始化。如果不 unmap 并解除对设备的控制，可能会在设备重启或驱动卸载/重新加载时产生冲突，导致设备行为异常。
*   *注：如果使用的是 `devm_` 前缀的托管函数（如 `devm_ioremap`），内核会在驱动卸载时自动 unmap，不需要手动处理。*

### 3. 用户空间映射 (User Space Mapping, 如 `mmap` 实现)
驱动程序通过实现 `mmap` 将内核内存或设备内存映射到用户空间。
*   **进程上下文问题**：通常用户空间调用 `munmap` 或进程退出时，内核会自动回收页表并减少引用计数。如果驱动在 `mmap` 时额外分配了内部管理结构（如 `vm_area_struct` 的私有数据），且没有在 `vm_open` / `vm_close` 中正确管理引用计数，不 unmap 会导致驱动内部结构泄漏。
*   **物理内存泄漏**：如果驱动为了 `mmap` 专门分配了物理页（如 `alloc_pages`），且在映射断开时没有释放，这些物理页将永久泄漏。

### 4. 内核虚拟映射 (Kernel Virtual Mapping, 如 `kmap` / `vmap`)
*   **Kmap 泄漏**：`kmap` 使用的是极其有限的固定地址空间（PKMAP_BASE）。在高内存（HighMem）系统中，如果不调用 `kunmap`，系统会迅速耗尽可用的 kmap 槽位，导致其他需要映射高端内存的代码死锁或崩溃。
*   **Vmap 泄漏**：`vmap` 同样占用 vmalloc 区域并消耗页表资源，不 `vunmap` 会导致内存泄漏和地址空间耗尽。

### 总结
在驱动节点中不执行 unmap，最直接的后果是**资源泄漏（内存、IOMMU页表、虚拟地址空间）**。在短期可能表现为内存占用增加；在长期或高频操作下，会迅速导致**系统资源耗尽、设备数据损坏、甚至内核崩溃**。

**最佳实践**：
1. 确保映射和取消映射严格配对（最好在同一个函数的退出路径或错误处理路径中处理）。
2. 尽量使用内核提供的**托管API**（带有 `devm_` 前缀的函数），这样在驱动卸载或设备移除时，内核会自动帮你释放资源，避免遗漏 unmap。
