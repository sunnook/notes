### 1. 为什么要依赖注入和反射？直接包含头文件调不行吗？

你的思想停留在 C/C++ 的**编译期决定一切**。在 C/C++ 里，你 `#include <header.h>`，编译器在编译时就知道这个类有多大、有什么方法，直接生成调用地址的机器码。这完全没问题，且性能极高。

但在 Java/Android 世界里，为什么需要反射和依赖注入？

**反射是什么？类提前生成了吗？**
*   **不是提前生成代码，而是提前生成了“元数据”。** 当 Java/Android 编译代码时，它不仅生成了字节码，还把类的结构（名字、有哪些字段、有哪些方法、参数是什么）作为一种“描述信息”存放在了内存的方法区中。这个描述信息就是 `Class` 对象。
*   **反射的作用：** 就是在**程序运行期间**，动态地去读取这些描述信息，并调用方法。
*   **为什么需要它？**
    1.  **解耦与动态加载（打破编译期依赖）：** 假设你写一个播放器框架，支持 FFmpeg 和 ExoPlayer 两个引擎。如果像 C++ 那样直接依赖头文件调用，你的主程序就必须在编译时写死调用哪个引擎。利用反射，你可以把引擎的类名写在配置文件里（或通过网络下发），程序启动时用 `Class.forName("com.xxx.FFmpegEngine")` 动态加载。主程序在编译期根本不需要知道 FFmpeg 的头文件。
    2.  **框架的基石（好莱坞原则：不要打电话给我，我会打给你）：** Android 的 `onCreate` 方法就是典型的反射回调。系统框架（Android OS）不可能在编译期知道你写的 `MainActivity` 有什么方法，所以它只能通过反射，在运行时去你的类里找名叫 `onCreate` 的方法并调用。

**依赖注入（DI）与反射的关系：**
你说的“外部实例化传进去”完全正确。但问题是，**“外部”怎么知道要 new 什么，怎么塞进去？**
如果是人肉写代码传进去，那叫“手动注入”。如果是用框架（如 Dagger/Hilt），框架为了能在运行时自动帮你把实例塞进去，它就必须去扫描你的类，看看哪里标了 `@Inject` 注解，然后通过**反射**动态实例化对象并赋值。所以，反射是实现许多高级 DI 框架的底层手段。

### 2. Rust 为什么学习曲线陡峭？借用检查器是什么？

Rust 陡峭，是因为它把 C/C++ 里程序员靠“经验和玄学”管理的内存问题，变成了**编译器强行拒绝编译的错误**。

**借用检查器是 Rust 编译器里的一个“暴君”模块。** 它在编译期严格检查三条铁律：
1.  **每个值同时只能有一个所有者。**（你把值传给另一个变量，原来的变量就失效了）。
2.  **可以同时有多个不可变引用（只读），但只能有一个可变引用（读写）。**（要么大家一起读，要么你一个人改，绝对不能边读边改，这消灭了数据竞争）。
3.  **引用必须始终有效。**（绝对不能出现悬垂指针，比如你返回了一个局部变量的引用，编译器直接报错不让过）。

**为什么陡峭？**
因为你以前写 C/C++ 甚至 Java，随便传指针、传引用是很随意的事。但在 Rust 里，你随便传一个引用，编译器就会疯狂报错，逼着你思考：“这个数据的生命周期到底归谁管？谁负责释放？这里会不会有并发冲突？”
你必须在代码里明确写出生命周期参数（`<'a>`），或者用引用计数（`Rc`/`Arc`）来安抚借用检查器。这种思维方式的转变极其痛苦。

### 3. 基于栈架构 vs 基于寄存器架构

这是虚拟机执行引擎的两种流派。假设我们要执行 `c = a + b`：

**标准 JVM（基于栈）：**
像是在算盘上打珠子，或者用一个栈做菜。
*   指令：`push a` (把 a 压入操作数栈) -> `push b` (把 b 压入栈) -> `add` (弹出栈顶两个数相加，把结果压回栈) -> `pop c` (把结果弹给 c)。
*   **特点：** 指令很短（甚至不需要写变量名，默认操作栈顶），编译器实现简单，但**执行同样的逻辑需要更多的指令**（频繁压栈出栈）。

**Dalvik / ART（基于寄存器）：**
像是在桌面上摆几个碗（寄存器），直接操作。
*   指令：`add v0, v1, v2` (把寄存器 v1 和 v2 的值相加，放进寄存器 v0)。
*   **特点：** 指令更长（需要指定寄存器编号），但**执行同样的逻辑需要的指令数少得多**（一步到位）。

**为什么 Android 选寄存器？**
早期手机内存小、CPU 慢。基于栈需要频繁读写内存（栈在内存里），而基于寄存器直接操作 CPU 的寄存器，指令数少，内存访问少，执行效率更高。代价是生成的 `.dex` 文件体积会稍微大一点点（因为指令里带了寄存器编号），但这是值得的。

### 4. 安卓也有进程树吗？系统进程都在树的上面？

**有，基于 Linux 的进程树。**

*   **根进程：** `init` (PID 1)。Android 手机开机内核启动后，启动的第一个用户空间进程就是 init。
*   **init 的子进程：** `init` 负责启动各种原生守护进程（如 `servicemanager`、`surfaceflinger`、`mediaserver`）以及最重要的 **`zygote`（受精卵进程）**。
*   **system_server 的位置：** `zygote` 启动后，第一个 `fork` 出来的子进程就是 `system_server`。AMS、WMS 等核心系统服务都跑在这个进程里。
*   **App 进程的位置：** 每次你点击图标打开一个 App，AMS 就会命令 `zygote` 去 `fork` 一个新进程。所以**所有的 App 进程，都是 `zygote` 的子进程**。

**结构图：**
```text
init (PID 1)
 ├── servicemanager (管家)
 ├── surfaceflinger (显示合成)
 ├── mediaserver (音频/相机服务)
 └── zygote (受精卵)
      ├── system_server (系统大总管，跑着 AMS/WMS 等)
      ├── com.android.xxx (你的 App 1)
      └── com.yyy.zzz (你的 App 2)
```
所以，系统进程并不在“树的上面”，而是**作为父节点或兄弟节点存在**。`zygote` 是所有 App 的父进程，这样设计的好处是：`zygote` 提前把 Android 核心库和虚拟机实例加载好了，App 进程直接 fork 它，就能瞬间继承一个 warmed-up 的虚拟机环境，启动极快。

### 5. 嵌入式定制系统的音视频 App 可以跨过 Framework 吗？

**完全正确！你的理解非常精准。**

我之前说的“App 拿不到硬件句柄”，是指**标准的、运行在沙箱里的第三方 App**（比如你从应用市场下载的微信、抖音）。

但如果你是在做**嵌入式平台定制开发**（比如海康的摄像头、车载 Android 主机、定制平板）：
1.  **系统级 App：** 你可以把 App 编译进系统镜像（`/system/priv-app/`），使用系统平台签名。此时你可以直接调用隐藏 API，甚至通过 JNI 直接调用底层的 C++ 服务。
2.  **直接调 HAL/内核：** 如果你有 root 权限或系统权限，你的 Native C++ 代码完全可以绕过 `CameraService`，直接打开 `/dev/video0` 节点，或者直接 `dlopen` 厂商提供的 `.so` 库，甚至直接操作 mmap 共享内存。
3.  **为什么这么干？** 极致的延迟和性能。Framework 层的 Binder 通信、权限校验、状态机流转都有开销。对于某些极度要求实时性的工业级音视频设备，直接跨过 Framework 操作底层是常规操作。

### 6. 安卓 App 通常有几个 Activity？每个都是进程吗？

*   **几个 Activity：** 没有固定数量。一个极简工具可能只有 1 个 Activity；一个复杂的电商 App 可能有几十个 Activity。但现代 Android 开发趋势是**单 Activity 架构**（一个 App 只有一个 Activity，所有的页面切换都使用 `Fragment` 或 Jetpack `Navigation` 来管理，这样能更好管理回退栈和生命周期）。
*   **每个 Activity 都是进程吗？绝对不是！**
    *   默认情况下，**一个 App 的所有组件（所有的 Activity、Service、Receiver）都运行在同一个进程里**，共享同一个主线程（UI 线程）。
    *   你在 AndroidManifest.xml 里不配置 `android:process` 属性，它们就死死挤在一起。
*   **能多进程吗？** 能。你可以给某个 Activity 或 Service 配置 `android:process=":remote"`。这样，当这个 Activity 被启动时，系统会为它单独创建一个进程。这通常用于“吃内存”的模块（比如网页渲染、大图浏览），把主进程崩溃的风险隔离掉。但对于绝大多数 App，都是单进程多 Activity 的形态。
