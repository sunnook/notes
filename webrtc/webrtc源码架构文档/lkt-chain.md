> **关键修正**：
> 1. **抖动缓冲** = `VideoStreamBufferController`（`video/video_stream_buffer_controller.cc`），核心函数 `InsertFrame` / `OnEncodedFrame` / `StartNextDecode`，内部用 `FrameBuffer`（`video/frame_buffer.cc`）做排序去重。
> 2. **到 VideoFrame 并未结束**：`VideoReceiveStream2::OnFrame` 生成的 `VideoFrame` 会继续经 `VideoBroadcaster::OnFrame` 分发到多个 sink（渲染、录制、编码器）。
> 3. **WebRTC 调用链列只放 C++ 原生文件**，Java 接口文件（`sdk/android/api/org/webrtc/*.java`）单独放到 `LiveKit→WebRTC 接口涉及文件` 列。
> 4. **JNI 桥接层**：LiveKit 调用的 `livekit.org.webrtc.*` Java API 经 JNI 进入 C++ 原生。JNI 桥接文件位于 `sdk/android/src/jni/*.cc`（如 `peer_connection_factory.cc`、`video_encoder_wrapper.cc`、`video_decoder_wrapper.cc`、`data_channel.cc`、`video_sink.cc`、`native_capturer_observer.cc`、`android_video_track_source.cc`），表中以 **[JNI]** 标注。

SetLocalDescription vs SetRemoteDescription — 关键区别


|   |   |   |
|---|---|---|
||SetRemoteDescription|SetLocalDescription|
|应用传输层参数|✓ 远端 ICE/DTLS 参数|✓ 本地 ICE/DTLS 参数|
|启动候选收集|✗ 不启动|✓ MaybeStartGathering()|
|启动 ICE 连通性检查|✗（等本地描述）|✓ 若远端已设置则启动|
|触发 onicecandidate|✗|✓ 收集到候选就回调|

核心逻辑：ICE 连通性检查需要两端都有描述才能开始。SetRemote 只存远端参数，SetLocal 才是"扳机"——先启动收集，若远端已就绪则同时启动检查+DTLS。主叫方 SetLocal(offer) 时远端还没到，只收集不检查；被叫方 SetLocal(answer) 时远端已设置，收集+检查同时启动。

## 补充：WebRTC 原生有、但 LiveKit 默认未上报的指标

`RTCMetricsManager` 的 `RTCMetric` 枚举**只上报**上表 10 项（freeze/pause、concealed、jitter buffer、quality limitation）。**RTT、丢包率、带宽估计这 3 类 LiveKit 默认不上报**，但它们都存在于 WebRTC 原生统计中，应用层可自行通过 `PeerConnection.getStats` 读取：

| 指标 | WebRTC stat 类型 | WebRTC stat 字段 | 原生采集来源 | 说明 |
|------|------------------|------------------|-------------|------|
| **RTT（往返时延）** | `candidate-pair` | `currentRoundTripTime` / `totalRoundTripTime` | ICE 连接（`p2p/base/ice_transport.cc`） | 基于 STUN 连接检查测得，当前/累计 RTT |
| **RTT（RTCP）** | `remote-inbound-rtp` | `roundTripTime` / `totalRoundTripTime` / `roundTripTimeMeasurements` | RTCP RR 反馈（`modules/rtp_rtcp/`） | 远端通过 RTCP Receiver Report 反馈的 RTT |
| **RTT（发送侧）** | `outbound-rtp` | `roundTripTime` / `totalRoundTripTime` | RTCP RR 处理（`modules/rtp_rtcp/source/rtcp_receiver.cc`） | 发送端基于收到的 RR 计算的 RTT |
| **丢包** | `inbound-rtp` | `packetsLost` | RTP 接收统计（`modules/rtp_rtcp/source/rtp_receiver.cc`） | 接收端累计丢包数（RFC 3550 有符号） |
| **丢包率** | `remote-inbound-rtp` | `fractionLost` | RTCP RR（`rtcp_receiver.cc`） | 远端反馈的丢包率（0~255 表示 0~100%），可换算为丢包率 |
| **带宽估计（发送）** | `candidate-pair` | `availableOutgoingBitrate` | ICE/端口分配（`p2p/base/port.cc`） | 发送方向可用带宽（bps） |
| **带宽估计（接收）** | `candidate-pair` | `availableIncomingBitrate` | ICE/端口分配（`p2p/base/port.cc`） | 接收方向可用带宽（bps） |
| **带宽估计（拥塞控制）** | （不在标准 stats 中） | `SendSideBandwidthEstimation` / `DelayBasedBwe` 内部状态 | GCC（`modules/congestion_controller/goog_cc/send_side_bandwidth_estimation.cc`、`delay_based_bwe.cc`） | Goog-CC 拥塞控制估计的发送码率，未直接暴露为标准 stat，需从 `RtpTransportControllerSend` 侧读取 |

> **结论**：LiveKit 的 `MetricsBatch` 上报**不含** RTT/丢包率/带宽估计。若需这些指标，应用层可：
> 1. 用 `Room.getPublisherRTCStats` / `getSubscriberRTCStats` 拿到 `RTCStatsReport`，读取 `candidate-pair.currentRoundTripTime`、`inbound-rtp.packetsLost`、`candidate-pair.availableOutgoingBitrate` 等字段；
> 2. 或自行扩展 `RTCMetricsManager` 的 `RTCMetric` 枚举与 `findXxxStats` 解析逻辑，把上述字段加入 `MetricsBatch` 上报。
