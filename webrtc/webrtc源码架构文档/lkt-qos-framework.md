# LiveKit QoS 框架分析与完整调用链表格

> 覆盖 LiveKit Android SDK（`livekit-android-sdk`）与 WebRTC 原生（`webrtc-m144_release`）两工程的 **QoS（服务质量）** 完整链路。
> 表头与 `lkt-chain.md` 一致：`阶段 | LiveKit 涉及文件 | LiveKit 调用链 | LiveKit→WebRTC 接口 | LiveKit→WebRTC 接口涉及文件 | WebRTC 调用链 | WebRTC 涉及文件 | 描述和备注`。
> 调用链格式：`类::函数` → `类::函数`；`**[JNI]**` 标注 JNI 桥接层（`sdk/android/src/jni/*.cc`，C++ 原生）。
> QoS = **主动控制机制**（RTCP 反馈驱动）+ **被动统计指标**（getStats 测量）。RTCP 包是两者交互的载体。

---

## 一、QoS 框架分析

### 维度一：QoS 控制机制（主动调节，RTCP 反馈驱动）

**上行（本端是发送者）——"发得稳"：**

| 机制 | 作用 | 核心类 | 触发 |
|------|------|--------|------|
| 拥塞控制 GCC | 估计带宽→目标码率 | `SendSideBandwidthEstimation`（丢包反馈）<br>`DelayBasedBwe`（延迟梯度） | 收到远端 RR / TransportFeedback |
| 码率自适应 | 按目标码率调编码 | `VideoStreamEncoder`（分辨率/帧率/QP） | 拥塞控制器输出 target bitrate |
| NACK 重传 | 补发丢包 | `RTPSenderVideo` + RTX | 收到远端 NACK |
| FEC | 前向纠错 | RED / ULPFEC / FlexFEC | 开启后随 RTP 发送冗余 |
| Pacing | 平滑发送 | `PacingController` | 每个包 |
| RTCP SR | 发送端报告统计 | `RTCPSender` | 定时 |

**下行（本端是接收者）——"收得稳"：**

| 机制 | 作用 | 核心类 | 触发 |
|------|------|--------|------|
| 抖动缓冲 | 排序/去抖 | `VideoStreamBufferController` / NetEq | 每帧到达 |
| 丢包检测 | 序列号空洞 | `RtpVideoStreamReceiver2` | RTP 到达 |
| RTCP RR | 接收端报告统计 | `RTCPSender` | 定时 |
| NACK | 请求重传丢包 | `RtpVideoStreamReceiver2::SendNack` | 丢包检测 |
| PLI / FIR | 请求关键帧 | `RtpVideoStreamReceiver2::RequestKeyFrame` | 解码失败 |
| REMB / TransportFeedback | 带宽/延迟反馈 | `RTCPSender` | 拥塞控制 |
| 错误隐藏 | 补丢帧 | NetEq concealment / 视频丢帧 | 丢包时 |

### 维度二：QoS 统计指标（被动测量，getStats）

**上行（outbound-rtp / media-source / candidate-pair）：** 发送码率、`packetsSent`、`bytesSent`、RTT `roundTripTime`、丢包 `packetsLost`、编码降质 `qualityLimitationDurations`、可用带宽 `availableOutgoingBitrate`。

**下行（inbound-rtp / candidate-pair）：** 接收码率、`packetsReceived`、`bytesReceived`、抖动 `jitter`、丢包 `packetsLost`、抖动缓冲 `jitterBufferDelay`/`jitterBufferEmittedCount`、卡顿 `freezeCount`/`pauseCount`、音频隐藏 `concealedSamples`、可用带宽 `availableIncomingBitrate`、RTT `currentRoundTripTime`。

### 维度三：RTCP 包（上下行交互的载体，PT 值已核实）

| RTCP 包 | PT | 方向 | QoS 作用 |
|---------|-----|------|---------|
| **SR** Sender Report | 200 | 上行发出 | 发送端报告发送统计（NTP/包数/字节数） |
| **RR** Receiver Report | 201 | 下行发出 | 接收端报告丢包/jitter，发送端据此算 RTT |
| **XR** Extended Report | 207 | 下行发出 | 扩展统计（丢包率、延迟等） |
| **NACK** | RTPFB 205, FMT=1 | 下行发出 | 请求重传丢失的 RTP 包 |
| **PLI** | PSFB 206, FMT=1 | 下行发出 | 请求关键帧（解码失败时） |
| **FIR** | PSFB 206, FMT=4 | 下行发出 | 强制全内请求（更强关键帧请求） |
| **REMB** | PSFB 206, FMT=15 | 下行发出 | 接收端反馈码率估计（旧式带宽反馈） |
| **TMMBR** | PSFB 206, FMT=3 | 下行发出 | 临时最大媒体码率请求 |
| **TransportFeedback** | RTPFB 205, FMT=15 | 下行发出 | 逐包到达反馈（GCC 延迟估计用） |
| **SDES / BYE / APP** | 202/203/204 | 双向 | 源描述/退出/应用自定义 |

> **RTCP 合并/分开原则**：所有 RTCP 包的**发送出口**都是 `RTCPSender` → `transport_->SendRtcp`（路径一致），但**触发点不同**。按触发点分组：SR（发送端定时）、RR（接收端定时）、NACK（丢包检测）、PLI/FIR（解码失败，同一触发点 → **合并**）、REMB（接收端带宽估计）、TransportFeedback（GCC 逐包反馈）。触发点一致则合并，不一致则分开。

## 四、WebRTC 原生有、但 LiveKit 默认未上报的指标

`RTCMetricsManager` 的 `RTCMetric` 枚举**只上报**上表 10 项（freeze/pause、concealed、jitter buffer、quality limitation）。**RTT、丢包率、带宽估计这 3 类 LiveKit 默认不上报**，但它们都存在于 WebRTC 原生统计中，应用层可自行通过 `PeerConnection.getStats` 读取：

| 指标 | WebRTC stat 类型 | WebRTC stat 字段 | 原生采集来源 | 说明 |
|------|------------------|------------------|-------------|------|
| **RTT（往返时延）** | `candidate-pair` | `currentRoundTripTime` / `totalRoundTripTime` | ICE 连接（`p2p/base/ice_transport.cc`） | 基于 STUN 连接检查测得，当前/累计 RTT |
| **RTT（RTCP）** | `remote-inbound-rtp` | `roundTripTime` / `totalRoundTripTime` / `roundTripTimeMeasurements` | RTCP RR 反馈（`modules/rtp_rtcp/`） | 远端通过 RTCP Receiver Report 反馈的 RTT |
| **RTT（发送侧）** | `outbound-rtp` | `roundTripTime` / `totalRoundTripTime` | RTCP RR 处理（`modules/rtp_rtcp/source/rtcp_receiver.cc`） | 发送端基于收到的 RR 计算的 RTT |
| **丢包** | `inbound-rtp` | `packetsLost` | RTP 接收统计（`modules/rtp_rtcp/source/rtp_receiver.cc`） | 接收端累计丢包数（RFC 3550 有符号） |
| **丢包率** | `remote-inbound-rtp` | `fractionLost` | RTCP RR（`rtcp_receiver.cc`） | 远端反馈的丢包率（0~255 表示 0~100%），可换算为丢包率 |
| **带宽估计（发送）** | `candidate-pair` | `availableOutgoingBitrate` | ICE/端口分配（`p2p/base/port.cc`） | 发送方向可用带宽（bps） |
| **带宽估计（接收）** | `candidate-pair` | `availableIncomingBitrate` | ICE/端口分配（`p2p/base/port.cc`） | 接收方向可用带宽（bps） |
| **带宽估计（拥塞控制）** | （不在标准 stats 中） | `SendSideBandwidthEstimation` / `DelayBasedBwe` 内部状态 | GCC（`modules/congestion_controller/goog_cc/send_side_bandwidth_estimation.cc`、`delay_based_bwe.cc`） | Goog-CC 拥塞控制估计的发送码率，未直接暴露为标准 stat，需从 `RtpTransportControllerSend` 侧读取 |

> **结论**：LiveKit 的 `MetricsBatch` 上报**不含** RTT/丢包率/带宽估计。若需这些指标，应用层可：
> 1. 用 `Room.getPublisherRTCStats` / `getSubscriberRTCStats` 拿到 `RTCStatsReport`，读取 `candidate-pair.currentRoundTripTime`、`inbound-rtp.packetsLost`、`candidate-pair.availableOutgoingBitrate` 等字段；
> 2. 或自行扩展 `RTCMetricsManager` 的 `RTCMetric` 枚举与 `findXxxStats` 解析逻辑，把上述字段加入 `MetricsBatch` 上报。
